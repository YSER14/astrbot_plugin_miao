# AstrBot 喵喵与米哈游游戏插件

状态：开发中，默认关闭。验收证据与开发计划文档不随插件发布，不能把本地开发状态当成已部署。

Python拥有AstrBot事件、账号、记录和任务生命周期；隔离Node进程复用锁定的MIT喵喵算法、数据及模板。没有Yunzai主进程或第二个QQ登录。上游代码和玩家数据放在插件数据目录，与本目录的适配源码分开。

本目录只是适配层源码：`main.py` 还要导入 `addons`、`databackup`、`ledger`、`notify` 这几个模块，运行还需要自备上游 miao-plugin 检出的运行目录，以及 Node ≥ 22.12、专用 Redis 与 headless Chromium。只拷本目录不足以启动插件。

回复投递不依赖框架补丁：`reply_policy.py` 是框架 `astrbot/core/utils/reply_policy.py` 的快照，`delivery.py` 在框架有该模块时用框架的、没有时用这份快照，所以干净安装的 AstrBot 也能加载本插件。改了框架那份，记得同步快照。

游戏帮助：`#帮助` 等同 `#喵喵帮助`，均显示喵喵帮助菜单。`bare_help` 仍默认关闭，用于控制“帮助”“菜单”“help”等更多通用别名；普通聊天里的“帮助”不会因此唤醒游戏插件。

开放范围：`all_groups` 允许所有已加入的群使用游戏功能，`all_private_users` 允许所有用户私聊使用游戏功能。源码默认关闭这两个范围开关；云端按主人授权开启。游戏处理器先接管识别出的游戏指令，普通私聊继续经过现有 PrivateGate；全局黑名单、会话停用和禁言规则仍生效。每个人的绑定、Cookie、设备上下文及缓存按实际 QQ 身份隔离，群聊和私聊均支持扫码，管理设置仍要求主人。

群里直接发 `#扫码登录`，二维码会引用本条指令发到原群；账号始终绑定给发起指令的 QQ。轮询检测到已扫描即撤回二维码，跳过该状态直接确认时也撤回；取消、替换、过期和卸载会再次清理尚未撤回的码。群二维码最多有效 90 秒，私聊默认 180 秒；确认登录后继续自动绑定和登记设备。撤回只使用本次机器人二维码的真实发送回执，不删除用户指令；撤回失败会提示检查，不影响已成功保存的登录。

面板出图时不再把上游快捷按钮转换成图片外的指令文字；扫码说明、失败提示、更新回执及无图片时的指令引导保留，图片内部内容不变。

统一面板更新：发送 `#更新面板`，已登录目标 UID 本人账号时优先读取米游社完整角色列表并分批获取详情；未登录或查询他人 UID 时保留原来的游戏展柜更新，米游社失败时也会明确提示后尝试展柜更新。原有 UID 参数、原神/星铁前缀和展柜服务选择保留，`#米游社更新面板` / `#mys更新面板` 作为同一流程的兼容别名。全角色更新原样保留接口字段并核对全部角色 ID；列表失败、详情缺项或某批报错均不当作全量成功，也不会把展柜缓存当作新获取的全角色数据。全角色成功后不重复用展柜数据覆盖。错误 5003 表示当前请求遭设备或安全校验拒绝，与交互验证码 1034 分开处理；仅凭 5003 不能确定根因，也不能保证补设备指纹即可恢复。

战绩设备上下文：`accounts.sqlite3` 的 `record_contexts` 按发送者、游戏、UID及登录凭据隔离保存已注册设备 ID、FP 与对应客户端头，查询通过 SDK 的构造参数加载，避免 UA/版本被 SDK 默认值覆盖。2026-11-03 云端本人账号已通过设备注册与手动验证，读取全部 86 个角色及 86 份详情；不需要读取用户手机信息。临时验证码证明、DS 和 Cookie 不进入静态请求头。同账号重新扫码时，仅当旧上下文仍有效，且新旧凭据的米游社账号 ID 与 V2 MID 一致、没有冲突时，在同一事务中续用原设备；更换账号、缺少身份字段、旧上下文已失效或手动替换凭据时不继承。解绑/删除登录会一同删除上下文。保留设备能避免重扫反复注册，但不保证免除官方安全验证。

扫码自动绑定后，`record_device.py` 复用固定 MIT Snap Hutao 的完整设备配置和官方 getFp 接口，为本次登录的国服原神角色准备匹配的设备上下文；已有匹配凭据的上下文直接保留。`record-device-profile.json` 记录固定来源，版权见 `THIRD_PARTY_NOTICES.md`，配置不读取用户手机信息。只在官方注册成功且角色列表返回 0 或 1034 时保存；1034 明确提示「设备已登记，待本人验证」，注册失败或 5003 保留已完成登录。该自动环节目前仅覆盖国服原神，星铁/绝区零自动绑定不等于设备与战绩功能已验收。

若需维护人员手动完成安全验证，沿用 Snap Hutao 的国服人工验证协议，先确认完整角色读取成功，再通过现有终端入口导入私有头文件：`account_admin.py ... --record-context <private-headers.json>`。此入口使用现有本人登录复查全部角色和分批详情，成功才保存，失败保留原登录与原上下文；文件不含 Cookie、DS 或 `x-rpc-challenge`。1034 仍需要在同一已注册设备上下文完成本人验证，不能只在手机 App 里点开战绩代替。

当前进度以实际测试结果为准。原喵喵65入口和genshin67条规则是验收基线，不是已支持的功能数量；文字前置提示和出图均不代表全功能已验收。

群内同角色排名：`#火神排名` 按喵喵原伤害规则比较本群成员的火神，`#火神评分排名` 按圣遗物评分比较。每次查询核对当前群成员，汇总其全部已绑定 UID（含非默认号），使用各自已经更新的角色面板；同一 UID 只占一条，重复缓存按角色更新时间合并。没有角色缓存的成员先执行 `#更新面板`。榜单仍受原全局开关、本群开关、参榜限制与显示条数设置控制。管理员可执行 `#刷新排名` 重建本群榜单。群视图按机器人、群和游戏隔离，退群或解绑账号在下次查询时排除；个人面板、登录凭据与私有战绩查询继续按发送者隔离，群排名不调用其他人的私有米游社接口。

预设（理论极限）面板：`#极限玛薇卡`、`#玛薇卡极限面板`、`#极限火神` 都认，另外 `核爆`、`辅助`、`平民`、`毕业`、`试用` 五个关键词同一套写法（`#玛薇卡核爆面板` 或 `#核爆玛薇卡`）。这条走梁氏那套固定预设 uid（`100000000`–`100000005`）：worker 把写法翻成原生 `#玛薇卡面板 100000000`，渲染仍是喵喵自己的面板页，预设数据随插件放在 `worker/presets/`，首次使用按需补进当前账号（带 @ 时补进被 @ 的人）的缓存目录，只补不覆盖；对预设 uid 不查米游社私有接口。缺数据或该角色不在这套预设里会直接说明：`「毕业」这套预设面板还没装数据` / `「极限」预设里没有「xxx」的配装`。星铁目前只装了「极限」，其余五个上游没有星铁数据。

@别人 查面板：指令前 @ 一个群友，查的就是那个人的面板，例如 `@群友 #火神面板`、`@群友 #更新面板`、`@群友 #面板列表`、`@群友 #圣遗物列表`。@ 只改查询对象：绑定 UID 从对方的绑定里取，面板缓存也读对方自己的目录，所以对方自己之前更新过的面板就是查到的那一份；对方没绑定会直接回一句带 @ 的提示让 ta 先 `#绑定 UID`，不会退回查发送者自己。给别人的更新只走公开的展柜接口（`#更新面板`），全角色米游社更新仍要求账号本人 `#扫码登录`，不会替别人使用其凭据；`#米游社更新面板` 对别人也一样只按展柜处理。抽卡记录、签到、私有战绩不吃 @——这些仍只按发送者身份执行，@ 不能当越权用。群排名类（`#火神排名`、`#最强火神`、`#刷新排名`）跟 @ 无关，仍是全群视图。

抽卡记录两条入口：`#导入抽卡记录`（把 UIGF 的 json 作为附件跟指令一起发出来，只读你自己这条消息里的附件，下载有 32 MB 上限，带 `authkey` 这类字段的存档直接拒收），以及按发送者隔离的终端入口 `record_admin.py`。导出只有终端一条。authkey 拉取、群文件清单式取得、原喵喵旧档 `data/gachaJson` 导入器都还没做。导入后 `#喵喵抽卡记录`、`#喵喵抽卡全部记录`、`#喵喵抽卡统计` 会由 worker 把本人记录落成原版 GachaData 认的按池 JSON 再渲染，所以这三条能出真图。

账号服务已接绑定/选择/解绑、凭据删除、三游戏便笺与手动签到的SDK适配。群聊或私聊直接发送 `#扫码登录`，无需预先绑定 UID；米游社确认后，SDK 查询该账号实际拥有的角色，自动绑定并保存原神、星铁、绝区零的受支持国服 UID，每游戏默认选择本次扫码角色中等级最高的一个。旧账号保留，当前选择切到本次登录的角色；`#uid` 查看、`#切换 序号` 切换，星铁/绝区零加对应前缀。可兼容 `#扫码登录 UID`，该 UID 只有确属扫码账号时才作为当前选择偏好，不匹配时仍自动选择实际角色。所有绑定和默认选择在同一事务中保存；没有受支持角色、角色读取失败或保存失败都不会留下部分绑定。海外暂通过 `account_admin.py` 终端隐藏输入导入。自动绑定与设备安全验证是两个环节，新账号战绩遭 5003/1034 时仍需独立处理。每游戏/区服分别验收，不能用原神登录成功推断其他游戏已通过。不要把 Cookie、密码或 authkey 发到聊天。

`wishes.py`提供按发送者隔离的抽卡记录存储、事务导入和导出；`record_admin.py`提供终端文件入口，`#抽卡记录状态`查看已导入记录。[UIGF标准](https://uigf.org/en/standards/uigf.html)当前为v4.2，三游戏记录保留大整数ID、原始时间与星铁21/22池。旧档缺物品ID或时区时会明确拒绝，不编造值；尚未做标准认证。QQ附件导入和原喵喵统计文件桥已有隔离测试，authkey取得/拉取等仍未完成。

星铁养成开发入口：`*养成计算 流萤 80 80 6 10 10 10`，兼容`*流萤养成`。`growth.py`使用独立rpgcalc接口，投影角色、已装备光锥及Point01—04四项行迹目标。图上的材料表在接口返回背包数时显示四列（材料/需要/拥有/还缺），`materials()`的总量不受影响，货币与无库存记录项显示「—」而不是 0。尾部加`全行迹`（或`全部行迹`/`额外行迹`/`解锁行迹`）才会把`skills_other`算进去，默认不算；compute 失败时会提示去掉这个后缀。主角同命途男女与强化形态的显示ID/服务ID分别处理；未核实的强化行迹不会冒充计算成功。当前通过合成回包、SDK签名契约与实际Chromium出图（含四列/两列两版）；**真实星铁账号、多UID与强化形态选择仍未验收**，额外行迹是否被 compute 接受也未验。这套改动**尚未部署到云端**。
